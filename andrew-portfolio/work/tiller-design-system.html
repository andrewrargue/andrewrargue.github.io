Case study

Building a Design System From Nothing

Three versions. Two years. The story of building a system that actually gets used — across 15+ client projects and a team of six.

Company

Tiller Digital

Role

Lead Designer

Years

2022–2025

Team

Vishu Mahajan (Head of Design), Ryan Kingston (Lead Developer), + 2 designers, 2 developers

Overview

At a web agency, every project started from scratch. No shared file structure, no component standards, no design/dev parity. Developers set styles from a single homepage. QA cycles ran 2–3 days per project. Output quality depended on who worked on it that week.

This was a direct agency profitability problem. I led the V1→V3 evolution — building the component architecture, designing the contribution governance model, and creating the video tutorials that made adoption stick.

Disciplines

Design Systems Component Architecture Token Systems Governance Design/Dev Parity

Business objectives

  • Reduce QA cycle time across all client projects
  • Establish consistent component standards agency-wide
  • Create design/dev parity between Figma and WordPress
  • Build a contribution model so the system grows with the team
  • Reduce dependence on individual designer judgment

The evolution

Three versions, each solving for what the last one revealed.

V1 — Nothing. Each designer set up files independently. Developers worked from a homepage. QA took 2–3 days. Output quality depended on the individual.

V2 — Structure without components. Shared file template with page organisation and grid specs. Reduced dev setup friction. But designers still made inconsistent component decisions — no design/dev parity yet. V2 revealed that structure alone wasn't enough.

V3 — Full system with governance. Atomic component library, primitive tokens, matched dev template, contribution model, status labels, video tutorials. QA drops to 1 day. Adopted as agency standard.

The problem

Nested groups eight layers deep. Eleven untracked hex values. Every designer starting from scratch.

Before the system, Figma files were structured differently by every designer. Nested groups eight layers deep replaced components. Ad-hoc fonts like Rubik appeared instead of the documented type system. Eleven untracked hex values existed with no semantic naming. Every designer made these decisions independently, every time — and developers had no shared reference to build against.

Before the system: nested Figma groups eight layers deep, ad-hoc fonts like Rubik instead of the documented type system, and eleven untracked hex values with no semantic naming. Every designer made these decisions independently, every time.

System architecture — Tokens

An 8px scale, semantic colour naming, and two swappable font slots.

8px base spacing scale with 12 named stops. Colour primitives named with semantic weight — Blue Grit-600 (darkest), Blue Grit-400-BASE (brand value), Blue Grit-200 (lightest).

Typography variables cover font family, weight, letter-spacing, and paragraph-spacing. Two font slots swappable per project. Grid documented at four breakpoints: 1920px (dev), 1728px (client presentation), 1440px (designer working), 375px (mobile).

I chose an 8px base unit because screen sizes and breakpoints divide cleanly by 8 — it gave us a consistent, predictable relationship between spacing tokens and layout grids, rather than arbitrary pixel values chosen per project.

System architecture — Spacing

A single 8px scale eliminates arbitrary spacing decisions across every project.

12 named spacing stops based on an 8px unit — from 8px (space-1) to 384px (space-12). Every component, section, and layout references named stops, never raw pixel values.

The result: spacing decisions are predictable, reviewable, and transferable between designers without conversation.

I chose named spacing variables over literal pixel values because design/dev handoff was breaking on raw values — developers and designers were referencing different numbers for the same intended space. Named tokens gave us consistency and removed a decision point from every single project.

System architecture — Typography

Two swappable font slots — one system that adapts to every client brand.

Font family, weight, size, letter-spacing, and paragraph-spacing all exposed as Figma variables. Two named slots — Primary and Secondary — swap per project without touching component internals.

Type scale follows a consistent ratio. Heading, body, label, and caption roles are named semantically so designers reference intent, not raw values.

System architecture — Grid

Four breakpoints, one shared reference — no more per-project grid decisions.

Grid documented at four breakpoints: 1920px for dev builds, 1728px for client presentations, 1440px as the designer working canvas, and 375px for mobile. Each breakpoint specifies columns, gutter, and margin.

Shared grid documentation meant developers and designers were always referencing the same spec — eliminating the breakpoint negotiation that happened on every V1 project.

System architecture — Components

Deliberately bare-bones — so brand application feels natural, not like fighting the system.

Intentionally wireframe-like components. Neutrality makes brand application feel natural, not like fighting the system. Figma component properties expose image position, dark mode, button visibility, icon position, and style variants — all configurable without detaching.

If a designer can't find what they need in 10 seconds, they'll build it themselves. Organisation is part of the system.

System architecture — Governance

Every project edge case feeds back into the library.

Formal contribution flow: Idea → Check library → Propose modification or full contribution → Kick-off → Collaborate → Review → Publish.

Video tutorials recorded for variable spacing and variable components. Ryan (Lead Dev) reviews new contributions before rollout, flagging implementation constraints.

System architecture — Workflow

Status labels baked into Figma — workflow tooling, not just organisation.

Ready for Dev, Awaiting Client Feedback, Needs Revisions, Approved — each frame carries its status as a visible label in Figma. Designers and developers share a single source of truth without switching tools.

Before status labels, handoff relied on Slack messages and email threads. After, the file itself communicated state — reducing the number of "is this ready?" conversations to near zero.

The system was adopted by the full team — Vishu Mahajan as Head of Design oversaw rollout, Ryan Kingston as Lead Developer maintained design/dev parity, and two additional designers and developers adopted it into their daily project work.

The file tells you what it needs. You don't have to ask.

Results

50–66% Reduction in QA cycle time — from 2–3 days down to 1
15+ Client projects built on the system
6 Team members adopted the system as agency standard
  • Design/dev parity between Figma and WordPress maintained across every project
  • Contribution model means the system grows from real project work, not theoretical planning
  • Status labels reduced ambiguity in handoff — designers and developers shared a common language
  • Video tutorials reduced onboarding time for new team members joining mid-project

V3 did not speed up individual project setup — that wasn't the goal. The win was consistency and reduced rework, not raw time-to-file.
