Case study

Redesigning WaitWell's Queue & Booking Experience

Designing an out-of-the-box default that felt polished, adapted gracefully across client brands, and met WCAG standards — while competing on UI quality against Waitwhile and QLess.

Client

WaitWell

Role

Lead Product Designer

Year

2024

Team

Sara Niniima (Product Design), Patricia Orozco (Art Direction)

Overview

WaitWell's flexibility — the ability for organisations to deeply customise their queue experience — had become a liability. Inconsistent UI patterns, unpredictable accessibility outcomes, and a queue page that lacked hierarchy left the core join and status experience feeling disjointed.

My focus: establish a scalable default that WaitWell could confidently put in front of enterprise and government buyers.

Disciplines

Product Design UX Audit Accessibility Mobile Design Systems

Challenge

  • End-user experience felt disjointed and unclear
  • Queue status page lacked hierarchy and engagement
  • Customisation options made UX consistency hard to maintain
  • Accessibility gaps across contrast, focus states, and text sizing
  • Needed to compete with Waitwhile and QLess on UI quality

Process — UX audit

Mapping where the experience broke down before touching UI.

Analysed end-user journeys for queue and appointment booking, mapped customisation pitfalls, and benchmarked against Waitwhile and QLess to find where WaitWell was underperforming — and where it had defensible advantages.

Four findings shaped the redesign priorities:

Brand elements competed with the primary action. The client logo and header repeated across nearly every screen, pulling attention away from the queue status — the thing users actually opened the app to see. I deprioritised brand placement on secondary screens and gave the queue status visual primacy.

Customisation had no guardrails. Clients could override fonts, colours, button hierarchy, and text case independently, which meant accessibility regressed silently whenever a client rebranded. This became the core argument for a token-based system.

The queue page lacked feedback hierarchy. Status, wait time, and available actions were flat and equally weighted, so users couldn't tell what mattered most at a glance.

Error and focus states were inconsistent or missing, which would fail WCAG contrast requirements as soon as a client applied their own colour palette.

The live product before redesign — entry screen, queue status, and notification experience. Client branding dominated the interface, queue status lacked hierarchy, and the primary update was a raw URL in a chat bubble.

Process — Wireframing

Three core flows rebuilt from the ground up.

I mapped three core flows — Find Existing Appointment, Walk-in, and Book Appointment — and used low-fidelity wireframes to reduce cognitive load, consolidate redundant steps, and improve wait-time visibility.

I made the queue status the dominant element on the post-join screen — large, centred, with wait time and position in queue visually separated from secondary actions like Message Us and Leave Queue. This directly addressed the audit finding that status had no hierarchy.

Process — Before / After

From scattered flows to a consistent, legible system.

Mapped three core flows: Find Existing Appointment, Walk-in, Book Appointment. Used low-fidelity wireframes to reduce cognitive load, consolidate redundant steps, and improve wait-time visibility.

Focus areas: consistent header and button hierarchy across all flows, smarter defaults, and clearer feedback states throughout.

Process — Visual direction

A system that stays consistent even when clients change the brand.

I explored colour hierarchy balancing WaitWell's default brand with client customisation flexibility — button and input treatments, iconography tone: friendly, accessible, trustworthy.

Three visual directions explored — default WaitWell branded, a neutral white-label option, and full client brand application. Each tier uses the same underlying component structure; only the surface tokens change.

The brand customisation model was designed to reduce the support burden on WaitWell's onboarding team, giving clients clear guardrails for what can be changed and what can't.

Clients get creative freedom without compromising UX integrity.

The same component structure applied across SKIMS and Home Depot — only the surface tokens change.

Process — Brand customisation

The same UI system, reskinned for any client in minutes.

Each tier is built on the same component structure — what changes is only what's visible on the surface.

Process — High fidelity UI

WCAG-compliant by default, not by retrofit.

I documented WCAG-compliant colour contrast and font sizing across the queue and booking flows, with visual progress indicators and consistent CTA structure across Join, Cancel, and Send Message actions.

The default system serves as the out-of-the-box demo version — the first thing a prospective customer sees in a sales conversation.

Process — Component library

Every interactive state documented — enabled, focused, disabled, active.

I built a component library covering every interactive element across the queue and booking flows — buttons, check-in controls, text links, document upload, dropdowns, form inputs, time selectors, checkboxes, and message actions.

Each component is documented across four states — enabled, focused, disabled, and active — giving the engineering team a complete reference for implementation without ambiguity.

No component ships without all four states defined.

Results

Shipped Live in production across WaitWell's customer base
Competitive Strengthened WaitWell's position against Waitwhile and QLess on UI quality
Scalable Customisation model that protects the core experience
  • Over a two-month engagement, audited 4 core flows and surfaced 90+ usability and accessibility findings
  • WCAG-compliant defaults gave enterprise and government buyers confidence in sales conversations
  • Defined a customisation model with clear guardrails — clients get brand flexibility without compromising accessibility or UX consistency
  • The default system now serves as the polished demo environment used in live sales conversations
